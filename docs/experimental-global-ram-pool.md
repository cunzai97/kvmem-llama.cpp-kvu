# Experimental global RAM-only KV pool and shared edit branches (not deployed)

This isolated candidate provides a process-local soft RAM budget for **trunk** packed-KV blocks across conversations. It does not deduplicate text or write KV to NVMe. It has a narrowly gated, suffix-only missing-page replay path, not general fragment reconstruction. The original vision-on-demand source and manager profile remain unchanged.

Launch separately with `kvmem-v100-exp/run-kvmem-global-ram-experiment.sh` (port 8792 by default); `KVMEM_EXPERIMENTAL_GLOBAL_RAM_BYTES` sets the soft trunk cap (default 8 GiB). The launcher disables runtime CPU/NVMe KV tiers and session files; isolated build uses `KVMEM_ENABLE_NVME=OFF`. It defaults to the normal MTP follower; `--spec-type none` is also supported. Never substitute this launcher for the live manager profile.

Each conversation still owns its own GPU slots, runtime, recurrent checkpoints, tokens and media history. When a middle-edit request has a media-aware common prefix, the server may fork at a **saved exact recurrent checkpoint of at least 128 rows**. Complete 128-row trunk blocks are shared by reference (packed K has the same original RoPE position); any partial checkpoint tail is privately copied. The MTP follower's packed-KV mirror shares the same complete prefix blocks separately and copies its tail; the corresponding MTP carry is restored from that checkpoint only after both mirrors have been checked and restaged. The old branch stays independently named and usable; source blocks are protected across detach→fork. Writes, truncation and invalidation copy on write. A missing checkpoint, incomplete packed attention/draft KV, or unsupported request falls back to normal full prefill, not an unsafe fork. A failure to allocate a child store returns an error rather than reusing/destroying the source branch.

The pool counts unique physical trunk block payloads by capacity and prioritizes **unshared (one-owner) cold blocks before multi-branch shared prefix blocks**, then LRU within that class. The active store and an in-flight fork source are pinned. On a block eviction the owning store is marked invalid until its bytes are validated. If **all** lost pages form a contiguous block-aligned suffix, all retained attention K/V and mean-K are complete, the retained MTP packed mirror is complete (when MTP is enabled), the incoming prompt matches the durable token/media prefix, and an **exact recurrent + draft-carry checkpoint** exists at the first missing row, the parked store is pinned and truncated at that row. Its intact physical prefix pages are not copied or regenerated; the prefill restores that checkpoint and evaluates only the missing suffix and new rows. Logs distinguish `store_suffix_recover` / `store_suffix_replay` from `store_suffix_fallback`. When the first missing page is at row zero, a complete/partial page follows a hole, a checkpoint is absent, or any verification fails, attach explicitly resets the store and runs normal full prefill. The old branch's name/history survives pool eviction, but its KV is not guaranteed hot. Recovery does **not** preserve a valid suffix across an internal hole. Branch retention further depends on the independent conversation-count/byte quota (use enough stores, e.g. 16, in this experiment).

**Limits / not production ready:** the cap counts trunk payload only, not the MTP follower mirror, GDN checkpoints, metadata, temporary allocations or GPU memory, and an active request can exceed it. Tail-copy vector capacities can include old suffix bytes that are no longer valid rows. Pool reconciliation scans all stores/blocks/layers after writes and repeatedly during eviction, which is unsuitable for long-context latency. Several allocation/write exception paths still need fault injection and fail-closed recovery work. Checkpoint retention is limited to four per conversation; not every desired edit position can fork. Image-path branch validation and long-context benchmarks remain open. General internal-hole fragment replay and incremental accounting have not been implemented; do not deploy as a bounded-RSS or fully branch-hot service.

**Verified:** isolated host tests 10/10, CUDA12/sm70 build, real V100 IQ3_S 27B on port 8792. With MTP enabled, an edited A→B branch at checkpoint row 645 shared five complete 128-row blocks, copied the five-row tail, logged `store_fork`/`store_fork_adapter` and `mtp_follow ... n_host=6 n_no_raw=0`; B's first request had 645 cache-hit tokens and A/B later each answered its own secret correctly with 834 cache-hit tokens. The same experiment without MTP also succeeded. Earlier forced-eviction tests confirmed whole-conversation miss on return (before this scoped recovery). New host eviction tests verify unchanged physical shared-prefix page identities, refusal to discard a live suffix, and regeneration of only missing suffix pages. A later isolated V100/MTP run with a 16 MiB trunk soft cap evicted two exclusive suffix pages after the A→B fork. On returning to A, logs recorded `store_suffix_recover rows=640 retained_blocks=5` and `store_suffix_replay ... keep=640 missing_rows=194`; the request hit 640 prefix tokens and evaluated 220 tokens (194 missing old rows plus 26 new prompt rows), answering A's secret correctly. B likewise recovered its suffix with a 640-token hit and answered its own secret. This verifies the suffix recovery path with real GDN/MTP, not internal-hole recovery or hard memory bounds. The five retained shared pages alone can exceed the 16 MiB soft cap while pinned. Exception safety, image paths and long-context behavior still need validation.
